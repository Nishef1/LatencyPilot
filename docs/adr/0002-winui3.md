# ADR 0002: Adopt WinUI 3 for the desktop UI

- **Status:** Accepted
- **Date:** 2026-09-12
- **Supersedes:** ADR 0001 only for the desktop UI framework and related deployment choice

## Context

ADR 0001 selected WPF to minimize deployment weight and project-start complexity. That trade-off was revisited before the UI became large.

Microsoft's current Windows guidance recommends WinUI 3 with the Windows App SDK for new native Windows desktop applications. LatencyPilot is Windows 11-only, expects increasingly rich telemetry/experiment views, and does not need a cross-platform UI layer. The project is still early enough that migration cost is low.

Windows App SDK 2.4.0 is the current Stable production-ready release as of this decision. Its unpackaged deployment model supports automatic runtime initialization through `WindowsPackageType=None`, and self-contained deployment can carry the Windows App SDK runtime with the application.

## Decision

Use:

- **WinUI 3** for `LatencyPilot.App`;
- **Windows App SDK 2.4.0 Stable**;
- an **unpackaged** desktop application (`WindowsPackageType=None`);
- **self-contained** Windows App SDK deployment (`WindowsAppSDKSelfContained=true`);
- **Windows 11 x64** as the release target.

The desktop application remains non-elevated. The privileged Windows Service boundary from ADR 0001 is unchanged.

The migration does not introduce an MVVM framework, dependency-injection container, navigation framework, second UI toolkit, or packaging system. Those require demonstrated need.

## Why WinUI 3 now

- It is Microsoft's current recommended native UI path for new Windows apps.
- It aligns naturally with Windows 11 and Fluent controls.
- LatencyPilot's future heat maps, device views, history, experiment-state UX, accessibility and high-DPI behavior benefit from the current Windows UI stack.
- The application is still small, so migration is cheaper now than after Phase 2/3 UX grows.

## Consequences

### Benefits

- Current Windows-native UI stack and Fluent control ecosystem.
- Better long-term alignment with Windows App SDK capabilities.
- No need to keep a legacy UI decision solely to save artifact size.
- UI modernization no longer becomes a future migration project.

### Costs

- Self-contained output is larger than the WPF artifact produced in Phase 1.
- Windows App SDK becomes a release dependency carried in the application output.
- Unpackaged WinUI publishing has more moving parts than plain WPF and must remain covered by CI/release validation.

## Deployment boundaries

The current release model is unpackaged and self-contained. MSIX is not introduced merely because WinUI supports it. A future installer may wrap the published output, but changing package identity/distribution semantics requires a separate decision.

`PublishSingleFile` is not enabled by default. It adds extraction behavior and extra publish constraints; use it only if distribution evidence justifies it.

## Testing impact

Changing UI frameworks does **not** justify growing the permanent automated suite. The repository-wide hard cap remains 10 permanent automated tests. Temporary implementation tests may be created for investigation and removed before merge/commit when they do not represent a lasting high-blast-radius safety contract.

## Rejected alternative: remain on WPF

WPF remains supported and mature, but its primary advantage here was lower deployment complexity. For a new Windows 11-only product whose UI is still small and expected to grow substantially, that advantage no longer outweighs long-term alignment with WinUI 3.
