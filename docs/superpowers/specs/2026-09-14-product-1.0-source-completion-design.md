# LatencyPilot 1.0 Source Completion Design

Status: Approved for execution by owner request to complete the product end to end
Date: 2026-09-14
Starting revision: `f0d8d7beb5878b012906080b447c53cc281ad5d7`

## Goal

Move LatencyPilot from its current measurement-first pre-alpha state to the maximum honest 1.0 source-complete state without weakening the project's physical-evidence, privilege, rollback, or CI contracts.

`Source-complete` means all software that can be implemented and deterministically verified from the repository is present and wired coherently. It does **not** convert owner-local hardware, WinUI/package, signing, or installer validation into fictional evidence. Any requirement that needs real Windows hardware or release credentials remains explicitly `implemented but not closed` until that evidence exists.

## Existing substrate to reuse

The current repository already has the major foundations and they must be composed rather than replaced:

- WinUI 3 observation/evidence dashboard and repeated baseline workflow;
- ETW DPC/ISR capture and module/processor attribution;
- `BenchmarkComparer` with explicit five-way verdict semantics;
- GPU affinity candidate generation from real baseline pressure evidence;
- exact GPU affinity snapshot/apply/verify/restart/rollback and durable SQLite journal;
- rollback-biased recovery and uninstall safety;
- exact-target allocated-interrupt/runtime placement verification tooling;
- PresentMon API discovery, device correlation and workload-metric capture;
- Raw Input → PnP ancestry → USBXHCI route discovery;
- present-device/driver/interrupt inventory and device relationship graph;
- self-contained release publishing and Inno Setup installer source.

No second UI framework, persistence engine, IPC stack, DI container, generic privileged executor, or generic tweak engine is introduced.

## Global safety boundary

The current public product protocol remains observation-only v6 and `MutationAvailable=false` until Gate A physical proof passes. Source work before that gate may complete ranking, metric interpretation, experiment scheduling, applicability detection, read-only subsystem discovery, recovery contracts and locked UI states, but must not make a user-reachable mutation command available.

After Gate A owner-local evidence exists, Gate B may add typed mutation-specific protocol v7 commands and mutation authorization. Gate C then physically validates that real App/client → Service boundary. Only Gate D may make supported mutation user reachable.

The design therefore distinguishes:

1. **source implementation readiness** — repository-verifiable;
2. **physical gate readiness** — implemented but owner-local evidence required;
3. **armed product capability** — only after all required physical gates.

## Slice 1 — Finish the GPU Go/Optimize decision engine

### Objective

Close the non-privileged orchestration gap between an authoritative Real-world baseline, the already-generated bounded GPU affinity candidates, ETW/PresentMon evidence and an explicit Keep/Restore recommendation.

### Design

`LatencyPilot.Benchmarking` owns optimization interpretation. Add a focused `Optimization` namespace with:

- a measurement set containing one primary `MetricSeries` plus named guardrail series;
- per-candidate evaluation using the existing `BenchmarkComparer` and `ComparisonPolicy`;
- fail-closed behavior when guardrail sets do not match the baseline;
- screening that never promotes `Tradeoff`, `Regressed`, `NoMeasurableDifference` or `Inconclusive` as an automatic winner;
- deterministic ranking of clean `Improved` candidates by relative primary improvement, then stable candidate identity;
- balanced finalist confirmation schedules (`ABBA` and `BAAB`) so order bias is not silently ignored;
- a final recommendation that is `KeepCandidate` only for a clean confirmed improvement and otherwise `RestoreOriginal`;
- raw comparison/provenance retained for UI/reporting rather than collapsed into a score.

PresentMon is integrated as guardrail evidence, not as a hidden composite score. Available frame-time/latency/dropped-frame metrics become named metric series; unavailable optional metrics stay absent and therefore cannot be invented. ETW DPC/ISR remains available as primary or guardrail evidence through the same metric-set contract.

Before Gate B, the App may prepare/display this plan but cannot execute mutation through product IPC.

## Slice 2 — Complete USB/xHCI and input analysis source

### Objective

Turn existing Raw Input/PnP ancestry discovery into authoritative read-only route evidence suitable for later reversible xHCI experiments.

### Design

Reuse `InputDeviceRouteReader`, `DeviceRelationshipGraph` and present inventory. Extend route evidence only with documented Windows semantics:

- keep stable Raw Input interface and PnP instance identity;
- retain full known ancestor chain and exact `USBXHCI` controller identity;
- where Windows exposes authoritative hub/port connection data through documented USB hub IOCTLs, capture the hub/connection context with explicit availability/error provenance;
- never infer a port, speed, message-signaled state or controller owner from names or registry hints;
- expose high-polling/report-rate evidence as observation, not physical click-to-photon latency;
- maintain partial-data behavior when topology cannot be resolved.

Any xHCI affinity mutation reuses the same journal/apply/verify/revert architecture only after the GPU experiment engine and physical safety boundary are credible; no generic device-registry writer is introduced.

## Slice 3 — Complete NIC/RSS read-only source and experiment readiness

### Objective

Add authoritative RSS capability/current-state evidence before any network mutation is considered.

### Design

Use Microsoft-supported RSS surfaces. Prefer the documented `MSFT_NetAdapterRssSettingData`/StandardCimv2 model for adapter-level state because it exposes enabled state, receive queues, interrupt messages, profile, processor range, indirection table and RSS processor data without inventing registry semantics. If a managed WMI/CIM dependency is needed, use Microsoft's `System.Management` package aligned with the repository's .NET 10 package family; do not add a second management framework.

Model:

- exact adapter identity and PnP correlation;
- RSS support/enabled/profile/current processor range;
- queue/interrupt/indirection evidence when exposed;
- availability/native/provider error provenance;
- no automatic claims when the provider omits data.

A later reversible RSS experiment must snapshot the authoritative original configuration, validate supported candidates and use the same journal/recovery discipline. It remains unarmed until physical benchmark and rollback evidence exists.

## Slice 4 — Cross-subsystem decision policy and workload profiles

### Objective

Reuse the GPU decision engine rather than create separate ad-hoc optimizers.

### Design

Introduce transparent profile/policy definitions that select primary metrics and guardrails for known workloads. Profiles may change which already-authoritative evidence is emphasized; they must never hide raw metrics, disable a guardrail silently or convert uncertainty into a numeric score.

Cross-subsystem selection is Pareto/trade-off aware:

- a candidate with a material guardrail regression is never called an automatic win;
- incomparable candidates remain a tradeoff rather than receiving an arbitrary weighted score;
- missing/insufficient evidence remains Inconclusive;
- exact original state remains the safe fallback.

History/reports store provenance and decisions using the existing evidence/journal boundaries; do not create another database abstraction merely for speculative analytics.

## Slice 5 — Productization and release hardening

### Objective

Make release source coherent and fail-closed without changing the CI policy.

### Design

Complete source-level release contracts:

- publishing includes only intended App/Service/docs/scripts payloads;
- installer preflight/upgrade/uninstall preserve recovery tools when state cannot be proven safe;
- release version/revision/provenance remain visible and auditable;
- checksums and signing hooks are deterministic and documented;
- migration/upgrade refuses to destroy unresolved recovery state;
- diagnostics/export provide enough evidence to troubleshoot release issues.

Hosted GitHub Actions remains test-only. App build, Service install/start, installer compilation, signing, upgrade/uninstall and GUI/accessibility checks remain owner-local evidence requirements.

## Test strategy

The hard permanent-test cap remains 10 and the current suite remains at 9 unless a later risk clearly merits the final slot. Prefer extending the existing high-blast-radius tests for shared optimizer invariants. Temporary RED/GREEN tests may be used during implementation and removed before final cleanup.

No CI solution build, WinUI build, installer build, GUI smoke or hardware claim is added.

## Execution order

1. GPU decision/orchestration engine and source-level Go readiness.
2. USB/xHCI/input authoritative read-only analysis.
3. NIC/RSS authoritative read-only analysis.
4. Cross-subsystem profiles and tradeoff policy.
5. Release/upgrade/uninstall source hardening.
6. Reconcile `ROADMAP.md`, `PROJECT_STATUS.md`, `SYSTEM_DESIGN.md` and user-facing docs against actual source.
7. Run final test-only CI on exact source-complete HEAD.
8. Produce one explicit owner-local closure checklist for all remaining physical/build/package/signing gates.

## Definition of source-complete

Source completion is achieved only when every repository-implementable 1.0 requirement has a concrete implementation or an explicit documented reason that implementation is physically gated by a prerequisite safety proof. No checkbox requiring physical hardware, WinUI/package execution, signing credentials or external observer evidence is checked solely because source exists.

The final product reaches true 1.0 only after the owner-local closure record satisfies those remaining gates.
